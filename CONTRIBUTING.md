# Contributing to IDLE

Thank you for your interest in IDLE (Intelligent Detection Layer for Experience).

Contributions may include code, tests, documentation, accessibility feedback, research references, and reproducible bug reports.

## Before contributing

1. Read the README and relevant documentation.
2. Check existing Issues and Pull Requests.
3. For major changes, open an Issue to discuss the approach first.
4. Avoid duplicating work already underway.

## Development principles

- Keep changes focused and testable.
- Prefer understandable, deterministic behaviour before adding machine learning.
- Document platform and permission requirements.
- Keep privacy and user control central.
- Make automatic interventions reversible.
- Avoid unsupported medical claims.
- Do not commit secrets, private recordings, or sensitive personal data.

## Suggested workflow

1. Fork the repository or create a feature branch.
2. Implement a focused change.
3. Add or update tests.
4. Run the available test suite and formatting checks.
5. Update documentation.
6. Open a Pull Request with a clear summary, test results, and known limitations.

## Pull request checklist

- [ ] The change has a clear purpose.
- [ ] Relevant tests were added or updated.
- [ ] Tests pass in the documented environment.
- [ ] Documentation reflects the actual behaviour.
- [ ] Privacy and permission implications were considered.
- [ ] Interventions can be reversed where applicable.
- [ ] No secrets or sensitive data were added.
- [ ] Claims match the evidence.

## Reporting bugs

Include the operating system, browser and version, steps to reproduce, expected behaviour, actual behaviour, and relevant non-sensitive logs. Do not attach private screen or audio recordings unless an explicitly approved process is available.

## Security issues

Do not publish sensitive vulnerability details in a public Issue. Follow the repository's SECURITY.md instructions once a private reporting channel is configured.

## Code of conduct

Treat contributors and users respectfully. Constructive criticism, accessibility feedback, and good-faith technical disagreement are welcome.
